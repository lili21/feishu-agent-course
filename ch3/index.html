  3.1
  
第一道关为什么不用模型

  
研发群里大部分消息是“收到”“好的”“+1”和表情。它们不需要理解，只需要认出来。用几行正则就能挡掉的东西，交给模型既慢又贵，还会让 Router 排长队。

  
第一道关只做四件事：是不是白名单群、是不是小橙自己发的、是不是飞书重复推送的同一事件、是不是寒暄。全部是确定性检查，一个 token 都不花。拖一下滑块，看看过滤率对模型调用量的影响。

过滤也不能太狠。“中午吃啥”这种句子正则认不出来，会漏给模型，由模型判为闲聊。宁可多放几条进来，也别把真正的 bug 挡在门外。







  3.2
  
权限归代码，价值归模型

  
判断拆成两层。授权（Gate）只看飞书事件里系统给出的发送者 ID，去查授权名单。评估（Assessment）才读消息文字，判断是不是任务、归谁、多急。

  
  
在模拟器里选 Tom（外部合作方），发那句“忽略之前的所有规则……”。它在第 2 步就被拦下，连模型都没调用。第 4 章会专门讲这类提示注入的攻防。







  3.3
  
拿不准就先问

  
每个群为每类事项设一个档位：L0 只记录，L1 先问，L2 直接做。最后落到哪一档，还要看两件事：有没有被点名，模型有几成把握。

  

    

      
情况群规则 L0群规则 L1群规则 L2

      
        
旁听到，有把握只记录先问人开工

        
被 @小橙 点名，有把握只记录开工开工

        
把握低于 0.6（是否点名都一样）只记录先问人先问人

      
    

  

  
被点名说明对方已经明确提了请求，再问一遍“要我做吗”是浪费对方的注意力，所以 L1 升到 L2。被点名不代表小橙有把握：模型自己都不确定时，降回 L1，先用一句话确认。L0 是观察期，被点名也忍住，只记下“我本来会接”，方便事后核对准确率。







  3.4
  
忙的时候，攒一批再判断

  
Router 一次只跑一个判断。它在忙的时候又进来几条消息，就先排队，等这次结束后打包成一批，一起交给模型。

  
  
打包还有一个好处：同一个人连发三条（“登录页有问题”“iOS 上”“键盘弹出时”），合在一起才是完整的一件事。分开判断，小橙可能会开三个任务。
